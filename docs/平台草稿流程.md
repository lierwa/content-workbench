# 平台草稿：新建、更新与恢复

适用于公众号和今日头条。平台动作由固定程序执行，内容判断与选图结果先冻结，不在点击、上传、保存、回读之间逐步调用 AI。

## 三个明确入口

| 入口 | 前提 | 结果 |
| --- | --- | --- |
| 新建 | 当前作品在目标账号没有草稿；查重已完成 | 新草稿 ID，完整回读通过 |
| 更新 | 已有草稿 ID、原账号身份和上次完整回读；当前版本已审稿 | 更新同一个 ID，完整回读通过 |
| 恢复 | 某一次操作中断或结果未知；保留原操作、版本、页面及证据 | 查明实际结果后完成原操作，不创建替代草稿 |

`PlatformAdapter.save_draft` 根据有无远端 ID 分流。更新统一进入 `draft_updates.run`，调用平台写入原语；不因检查失败退回新建。新建仍复用原有路径。

当前实际验收覆盖两平台的原稿配图、封面和排版更新。公众号标题或文字变更仍由平台写入入口拒绝，不属于已支持范围；不能用本次配图成功推定所有编辑更新均可用。新增更新能力应接入本流程的原稿检查、版本绑定、保存检查点和回读，不另起重试分支。

## 更新状态与绑定

每次更新固定绑定 operation_id、account_id、platform、draft_id、平台身份、revision、content_hash。日志保存在账号目录下 `draft-updates/<operation_id>.json`，不进入 Git，不含密码或 Cookie。

1. `checking_original`：从草稿箱打开绑定 ID，核对账号、原标题、正文、图片、封面及声明。图片临时签名变化不视为改稿，资源本身变化仍拒绝。
2. `writing`：在已核对的原编辑页替换正文和图片、更新封面。必须选中并替换原正文，不能追加第二份全文。每张图保留本地哈希和平台地址映射。
3. `saving` → `saved`：保存前先持久化图片映射与封面回执，再执行保存。已有草稿 ID 本身不是本次保存成功的证据；保存中断时先独立回读，不能直接再点保存。此时不能称为完成。
4. `verified`：重新打开同一个 ID，核对当前版本的标题、全文、图片数量/位置/内容、封面和账号。只有这一阶段算更新完成。

检查失败记 `check_failed` 或 `original_changed`，不会写入。写入结果不明记 `outcome_unknown`，同一操作不能自动再写一遍。远端 ID 改变立即停止后续操作。

## 恢复原则

- 先读状态，不靠新建窗口、会话或同名草稿恢复。
- 本地选图计划按正文、材料版本、选图规则和兜底资产哈希缓存；两平台复用，进程重启不重复选图。
- 平台写入恢复只接受匹配原操作 ID、版本与内容哈希的上下文。
- 已保存且回读一致：直接确认。原稿确实未变：允许重新执行该更新。保留的失败正文与当前页面完全一致：按该检查点续作。无法对应或有人改稿：保留现场，停止覆盖。
- 同一内容版本重复请求：重新核对原稿后直接返回，不重复上传、写入或新建。未保存完的公众号编辑页先按记录恢复，后台检查不能先刷新该编辑页。
- 多图只上传了一部分时，逐张验证原位置、图片内容和已上传资源，再补余下图片；封面已选择完成时跳过已完成的选择步骤。
- 工具明确返回未执行，并且重新观察证明输入内容没变时，只允许一次受限重试。执行效果未知时先读实际结果，不重放。

## 共用原语与资源

两平台共用流程绑定、任务队列和回读验收；各自保留账号识别、编辑器定位、上传图片、替换正文、选择封面、保存以及读取草稿的固定原语。一次任务复用一个 BrowserSkill 会话，平台写入与回读串行，选图不占浏览器。

浏览器通道失败与草稿业务结果分别记录：已经独立回读通过的草稿，不因之后的截图失败变成未保存；写入中断的草稿也不能因工具恢复连接就变成已完成。工具报告 idle 只表示没有排队操作，不能替代一次真实读操作。连接失败时保留更新日志，不通过新建会话、同名新稿或无限重试掩盖错误。

## 验收要求

同一批既有草稿完成多图更新并保持 ID 不变；文字和审稿结果不因配图改变；中断后按记录续作；重复请求不产生新稿；真实外部改稿仍被拦截；失败记录保留。各项真实执行结果写入 `全流程验收-20261101.md`，本文件定义流程，不代替通过证据。
