# 栏目驱动生产：设计与实施

日期：2026-11-04。本文保留前一轮栏目化开发及局部验证记录。后续发现的编辑标准混用、自动补筛、时间与来源要求，以及最终清库实跑条件，统一以 [栏目编辑策略与全自动出稿验收](栏目编辑策略与全自动出稿验收.md) 为准。下文的“本轮”指当时的开发轮次，其完成记录不代表新的完整验收通过。

## 目标与现状

栏目是生产配置的归属单位：从共享池按自己的渠道和时效取材，按自己的规则筛选、选稿、创作、返修、独立审稿和配图排版。题材、筛选方式、成稿形式相互独立。科技可以写单篇，热点可以做集合；业务代码不能识别栏目名称决定行为。

现有实现已有共享池、栏目三筛规则、写作要求、账号目标和任务快照，但存在以下断点：

| 位置 | 当前问题 | 本轮改动 |
| --- | --- | --- |
| draft_selection | 集合选稿强制主稿和共同问题，其余独立消息被排除 | 每条独立判断，按栏目数量及不足策略组稿 |
| composition / editorial | 全局单篇指令覆盖集合；审稿未检查条目结构 | 统一传递栏目要求，文字审稿增加栏目验收与实际结构检查 |
| images / typesetting | 配图、段落规则不能随栏目设置；缓存未绑定这些要求 | 栏目独立规则与结构化配图选项，缓存包含实际配置 |
| workspace | 只有采集、筛选定时；没有出稿截止时间 | 复用现有调度器，增加提前准备、期次和截止状态 |
| candidates | 选稿记录 sent 永久渲染为「已入队」 | 关联真实制作任务，区分制作中、已成稿、需处理及平台状态 |

## 集合稿参考与可编辑起点

2026-11-04 已核读的样本：少数派 [11 月 3 日派早报](https://sspai.com/post/118232) 有 5 条主消息，部分消息配图；[界面 AI 早报](https://www.jiemian.com/article/15288958.html) 有 6 条消息，无正文图；[爱范儿早报](https://www.ifanr.com/1687477) 有 27 条消息，较多图片；[36 氪 8 点 1 氪](https://www.36kr.com/p/4054687391143044) 有 37 条消息，分类组织，无正文图。计数不含广告、目录重复和推荐阅读。这些样本说明不存在统一的行业条数或逐条必须配图的要求。

提供可编辑的形式模板：集合默认目标 10 条、范围 8–12 条，每条 120–220 个非空白字符，最多 2 段，独立小标题；每条说清主体、最新变化、关键事实、状态与来源，不足信息不扩写。图片按需要选择，封面和正文图片分开设置。以上是产品起始值，不是行业规则，均保存在 JSON 模板及栏目配置中。用户可改数量、字数、段落、结构、图片策略；不会因栏目叫「科技简报」自动套规则。

集合中的多篇报道可能属于同一事件，应合并为一条简讯；Apple 与千问若是同一合作事件，不能据两个品牌算两条。每条独立消息不需要回答同一个问题。集合贡献是可靠的取舍、压缩和编排，不能按单篇长文的论证要求退稿。

## 配置契约

保留已有字段，避免第二套同义配置：`rules` 定位、`screening_rules` 三筛、`draft_rules` 选稿、`writing_rules` 写稿。新增 `production_rules` 保存补证、返修、审稿、配图、排版的栏目指令；空值表示使用通用执行契约，不表示跳过事实核验。

`format_policy` 保存条目目标/上下限、不足策略（等待或允许少量成稿）、每条字数上下限、段落上限、小标题/结构要求、正文图策略及上限、封面策略。集合至少两条独立消息；一条只能作为单篇另行制作。`draft_limit` 继续控制单篇每轮篇数；集合每期一篇，其条数由 `format_policy` 决定，不混淆两种计数。取材上限与成稿目标分开，保存时检查是否足够。

全局层只保留事实、出处、未核信息、数据不作为指令、输出证据及平台硬限制等共用约束。栏目层决定内容取舍和表达。模型连接、密钥与角色配置继续共用，不复制到栏目；实际调用仍保存模型快照。

筛选运行冻结筛选配置；选稿冻结完整栏目配置，制作继承该快照与选稿结果。运行中修改写作、返修、审稿、配图和排版规则只影响下次选稿；数量目标、结构或形式改变时，相关筛选依据也须更新；已出稿内容、来源和账号身份不变。排版、配图和审稿复用须匹配对应配置及文字/材料版本。

## 定时、期次与失败

增加栏目 `production_schedule`：关闭/每天/每周、目标出稿时刻（北京时间）、提前准备分钟数、交付方式（本地成稿或同步平台草稿）。示例：08:00 集合稿可提前 60 分钟准备，12:00 单篇可提前 45 分钟准备；示例不自动启用。

采集仍由共享采集计划持续入池，栏目准备从已配置渠道的池中选取内容，不重复启动一套采集器。页面提示采集需先设好。出稿计划启用时替代本栏目的独立筛选定时触发，防止同栏目双重定时；手动筛选保留。

期次键为栏目与目标时刻，先持久化再派发；重启通过该键找回原批次，不重复创建。忙碌时在截止前等待，过期不补发；停止和停用尊重用户操作。材料不足时按栏目策略等待或少量出稿，不能填旧闻。错过截止时保留本地结果、显示逾期；不得为了赶时间跳过审稿或未经核验自动投递。同步结果未知沿用现有回读机制，不重复创建平台草稿。

**公开发布是独立能力**：当前 Wechatsync 适配器只完成草稿保存与回读，本轮不新增未验证的自动公开发布操作。出稿安排只能选择已实现的交付方式。公开发布仍需平台能力、身份和当前稿件确认；这次开发不发布真实内容、不启用真实定时。

## 界面与迁移

栏目编辑依次提供内容范围、三轮筛选、选稿与创作、形式与图片、定时交付。栏目卡片显示形式、条数及目标出稿时刻。所有字段由统一栏目接口保存，带 revision 防止覆盖并发修改。

旧栏目和任务不删除、不重写；读取旧配置时补足新字段的默认展示值，已有自定义指令保留。旧取材上限低于新集合需求时显示需调整，保存时校验，不能偷偷扩大模型调用预算。现有实际稿件不会被此变更自动重做。

选题列表状态从 batch + event/集合成员 + 实际 job 关联。一个集合内的成员显示同一作品状态；多个平台分别完成时显示汇总及明细，不用选稿 sent 代替制作状态。集合摘要显示「N 条消息 → 1 篇集合稿」，不把条数说成稿数。

## 实施与验收

按配置及文档 → 提示词与格式验收 → 调度与快照 → 状态及界面顺序实施。使用临时目录与模拟模型/平台返回检查四种筛选方式和形式组合、集合不足/超限、配置冻结、排版图片策略、跨天计划、重启去重、停用与逾期；不新增测试文件，不调用真实模型或平台写入。执行 Python 语法检查、前端构建及差异检查，记录结果及未实测的边界。真实账号状态和现有业务数据保留。
